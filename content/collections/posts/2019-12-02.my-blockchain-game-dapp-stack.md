<p>I am writing this post because this is the type of information I had trouble finding when I first set out to build a blockchain game. In this blog post, I describe the software stack I'm using to develop <a href="http://orbiter8.com">Orbiter 8</a> and why I made the choices I made along the way. This is by no means a recommendation to follow down the same path. However, there may be value in sharing the lessons I've learned along the way.</p>
<p class="has-medium-font-size">Summary</p>
<p>Orbiter 8 is a Web 3 game dapp for the <a href="https://ethereum.org/">Ethereum network</a>. The game is accessed through a Web browser and requires some form of Ethereum wallet such as <a href="https://metamask.io/">Metamask</a>. The JavaScript client uses <a href="https://vuejs.org/">Vue.js</a> to render a dynamic SVG-based game world. Interactive game world objects - including planets, moons, starports, and ships - are all stored and manged on the Ethereum blockchain through <a href="https://github.com/ethereum/solidity">Solidity smarty contracts</a>. Only, I don't do development directly on the Ethereum blockchain because that would be expensive. Rather, I use the <a href="https://www.trufflesuite.com/">Truffle suite of tools</a> to create a local environment to develop, test, and deploy smart contracts on a local test network, public test network, and - eventually - the live Ethereum network. Outside of the game itself, I use PHP, MySQL, <a href="https://laravel.com/">Laravel</a>, Bootstrap and other related technologies for the game's website (and a future Web 2.0 companion site). And finally, my IDE of choice is MS Visual Code, browser of choice is Firefox, and OS of choice is Ubuntu.</p>
<p>The three most interesting choices I made here are all on-chain with Ethereum, Vue.js w/SVG, and Truffle for Web3. I'll go into more detail for each of these.</p>
<p class="has-medium-font-size">All On-Chain With Ethereum</p>
<p>There's a lot to break down here. Let's stat with "all on-chain" and what I mean by that. It took me longer to understand what the Ethereum network does than Bitcoin. With Bitcoin, the metaphor of money and ledgers helped make sense of what the system was trying to do. Ethereum and networks like it are a new kind of thing.</p>
<p>The Ethereum network provides a giant computing system called the Ethereum Virtual Machine or EVM. The EVM runs chunks of code called "smart contracts" that can do basic compute and, for a fee, write some resulting data to the blockchain. For Web 2.0 app developers, you can imagine the blockchain as your datastore (i.e. MySQL) and smart contracts are sort of a cross between to your traditional "backend services" and the concept of "database triggers" available in many relational databases. Then mix into all of this that the currency the network is designed to support is also used to pay for those previously mentioned writes to the database. Why is that interesting? For starters, if you manage to make your game run entirely on the network, you game no longer requires a Web server to remain online. These new kinds of applications are called decentralized applications or "dapps" for short. </p>
<p>All of Orbiter 8's core gameplay happens within smart contract code, making it a proper dapp. The game client interacts with the dapp contracts to trigger moves in the game and return data about the game state. Then the client renders a game world representing known data about the current game state. A third party could, potentially write a completely different looking game client that works against the same dapp on the network, being effectively the same game. I find this model compelling.</p>
<p>Ethereum is not the only blockchain with a virtual machine and Turing complete smart contracts. I often get asked why I do not use one of many other platforms such as <a href="https://code.visualstudio.com/">Tron</a> and <a href="https://eos.io/">EOS</a> and many others. Sometimes I have specific issues with a platform. For example, I believe that having transaction fees that go to miners is the right incentive model for a network and that, despite the challenges involved in building UX around it, it is an important feature to support. However, more generally speaking, I choose Ethereum because it was here early and lots of people are holding the ETH currency. A game needs an audience and I think the Ethereum community needs games!</p>
<p>Ethereum and the Solidity language do have their limitations. I have run into problems where my contracts are too long and run out of gas or my function manages too many variables and I have to stuff some things in an array to avoid blowing the stack. I do think it's possible that some other platform will eventually replace Ethereum (I'm look'n at you, <a href="https://www.cardano.org/en/home/">Cardano</a>). However, due to the open source nature of Ethereum and the forkability of the network itself, it's hard to imagine that the platform won't continue to grow and improve even as I develop the game itself. </p>
<p class="has-medium-font-size">Vue.js for SVGs</p>
<p>The choice to use Vue.js came easily as it is the most robust front end framework I know how to use. <a href="https://reactjs.org/">React</a> seems to be a more popular alternative in the development community. However, using React would require learning yet another thing when I'm doing a lot of learning already. Also, Vue.js is really pretty decent.</p>
<p>The place where things got weird comes with the way I decided to use SVGs. It wasn't an entirely new idea for me. A few years before I started this game I noticed that Vue.js can manipulate the contents of an embedded SVG file like any other nodes in the DOM. By creating SVG groups and layers, I could rotate and scale things on the fly just by changing a single variable in the SVG which was tied to a value in the <a href="https://vuex.vuejs.org/">Vuex</a> data store. </p>
<p>From a developer perspective, this is a really cool way to rapidly build an interface. It's much simpler than dealing with the canvas renderer or trying to learn a new library like <a href="https://threejs.org/">Three.js</a>. The resulting scene looks super sharp and can export to a screenshot that scales up without deteriorating. </p>
<p>Unfortunately the SVG approach isn't without some challenges. Web browsers do not render SVGs terribly fast, making it difficult to draw a reasonably complex scene at a high enough framerate to look nice. I started pressing up against the limitations of how many objects I can draw on the screen at any given time early in the development process. </p>
<p>In the long run, I may need to abandon my SVG approach due to performance issues. However, I still feel optimistic that I can improve the performance of my rendering. Given that I'm still working towards a beta, I have note invested much time in optimizing graphic performance.</p>
